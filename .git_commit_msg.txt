fix(download): 修复 .part 协议的三个连锁问题(v1.2.6)

v1.2.5 引入 .part 原子落盘后, 三处未同步适配的地方被暴露出来:

1) 进度条卡 0%
   /api/download 给 downloads.path 填的是最终名 xxx.iso, 而 iso_runner 打印
   的 #TARGET 哨兵用 .part 名。running_task() 对最终名 stat() 得 0, 且
   targets.get(最终名) 取不到 -> got=0/total=0 -> 进度恒 0%。
   修: api_download 统一用 PART_SUFFIX 拼 .part 路径, 两端 key 对齐。

2) .part 被误报为"过期文件"
   disk_inventory() 第一趟循环无差别收录目录所有文件(含 .part 原始名),
   第二趟又把同一文件归到目标名下。于是 .part 原始名进了 stray_files, UI
   显示"不在最新清单元数据中(通常是已被更新淘汰的旧版 ISO)"并给出
   「清理过期」红按钮 -- 而它其实是正在下载/可续传的半成品。
   修: 第一趟跳过半成品后缀; build_distros 对 partial 再做兜底过滤;
        local_total 按物理文件去重(半成品与同名完整文件不重复计数)。

3) 重下后状态不变 + 没有真正续传
   注释一直声称"可续传", 但 _download_file_with_failover() 始终以 "wb"
   打开 .part(截断), 每次从 0 重下 -- 续传是假承诺。
   修: 实现真正的 HTTP Range 断点续传:
       * 有 .part 时发 Range: bytes=N-
       * 服务器 206 -> "ab" 追加写入; 200(不支持) -> 告警并从头下, 避免拼接错
       * 416(断点越界) -> 报错重下
       * 校验失败 -> 丢弃损坏半成品, 避免下轮拿坏数据续传
   另: 前端 poll() 任务运行期间每 5 秒刷新一次列表(此前只在任务结束那一刻
   刷新, 用户下载中途看列表会以为状态没变)。

涉及 iso_download/download_linux.py(订阅同步路径)同步改造。

测试: 新增 5 例续传用例(Range 头/206 追加/200 回退/中断保留/坏块丢弃)、
4 例 stray 与去重用例、1 例前端运行中刷新契约; 修正 2 例因行为改进而过时的
断言。全量 185 例通过。本地端到端复现: 限速 Range 服务器跑到 3MB 杀进程 ->
第二轮发 Range: bytes=3145728- 续传 -> 最终文件恰好 8388608B 完整。
