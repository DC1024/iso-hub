# 备份与恢复

ISO Hub 的全部"不可重建"的状态都在 `./data` 下的**四个 JSON** 里。ISO 本身不在此列 ——
几 TB 的文件该由 NAS 快照或备份策略负责，把它们塞进配置备份只会让备份越滚越大。

| 文件 | 内容 | 丢了会怎样 |
|---|---|---|
| `settings.json` | 账号、会话、邮件通知、qB 地址与凭据、共享凭据、定时任务 | 要重新建号、重配通知与共享 |
| `distributions.json` | 发行版清单（含自定义源） | 自定义源全部消失，需重新添加 |
| `gpg_ledger.json` | 验签账本（每条目 pass/fail 与时间） | 健康面板归零，需要重跑补校验 |
| `download_unverified.json` | 未验签 / 校验不符记录 | ⚠ 徽标丢失，但文件仍在 |

## 为什么必须做

开启 `settings.json` 静态加密（`ISO_HUB_SECRET_KEY_FILE`）之后，**密钥与密文任一丢失都
不可恢复**：加密是一次性的，没有后门，也没有"忘记密码"流程。加密之前先有可用备份，
顺序不能反。

## 备份

脚本随镜像分发，容器内直接可用：

```bash
# 默认写到 /data/backups/，保留 7 份
docker exec iso-hub python /app/scripts/backup.py

# 保留 14 份，输出机器可读 JSON（便于 cron 采集）
docker exec iso-hub python /app/scripts/backup.py --keep 14 --json

# 只看看会备份什么，不落盘
docker exec iso-hub python /app/scripts/backup.py --dry-run
```

输出示例：

```text
[backup] 已写入 /data/backups/isohub-backup-20261022-004512.tar.gz (4.2 KiB)
[backup] 内容: settings.json, distributions.json, gpg_ledger.json
[backup] 不存在, 跳过: download_unverified.json
[backup] 清理旧备份 1 份: isohub-backup-20261001-030000.tar.gz
```

外部调用（宿主上有 Python 时）：

```bash
python scripts/backup.py --data-dir /path/to/data --keep 30
```

### 放进 cron

```bash
# 每天 03:30 备份一次，保留 30 份
30 3 * * * docker exec iso-hub python /app/scripts/backup.py --keep 30 >> /var/log/isohub-backup.log 2>&1
```

`download_unverified.json` 不存在时不算失败（本来就可能没有未验签文件）；但
**`settings.json` 不存在会以退出码 3 失败** —— 那说明 `--data-dir` 指错了，不是"空配置"。

### 备份放哪

`/data/backups/` 是默认位置，权限 `0700`。它和 ISO 在同一个卷上，**同盘备份挡不住盘坏**，
建议再同步一份到别的机器：

```bash
# 极空间等 NAS 上，把备份目录同步到另一块盘或远端
rsync -a /path/to/data/backups/ /另一块盘/isohub-backups/
```

### 加密密钥要单独保管

开了 `ISO_HUB_SECRET_KEY_FILE` 之后，**密钥文件不能和备份放在一起** —— 否则拿到备份的人
同时拿到密钥，加密就白做了。建议：密钥放 `/run/secrets/` 或仅 root 可读的位置，
备份走另一条链路（或对备份本身再做一次加密）。

## 恢复

恢复是破坏性操作，默认**只预览**：

```bash
docker exec iso-hub python /app/scripts/restore.py /data/backups/isohub-backup-20261022-004512.tar.gz
```

确认内容无误后加 `--yes`：

```bash
docker exec iso-hub python /app/scripts/restore.py /data/backups/isohub-backup-20261022-004512.tar.gz --yes
```

脚本会做三件事：

1. **白名单校验** —— 归档里只允许那四个文件名。出现 `../settings.json`、绝对路径、
   目录成员或符号链接一律拒绝（退出码 2），不依赖 `tarfile` 的 filter 版本差异。
2. **先存旧** —— 覆盖前把当前文件复制到 `/data/backups/pre-restore-<时间戳>/`，
   恢复错了还能退回去。
3. **原子写 + 收权限** —— 先写 `.restore.tmp` 再 `os.replace`，恢复后的文件统一 `0600`
   （里面有会话 token 与 SMTP 授权码）。

恢复完成后重启容器使配置立即生效：

```bash
docker restart iso-hub
```

## 验证

```bash
# 服务活着、数据目录可写
curl -s http://127.0.0.1:8899/api/health | python -m json.tool

# 账号还在、通知配置还在（password 不会回显，只看 password_set）
curl -s -H "X-Auth-Token: <token>" http://127.0.0.1:8899/api/shares
```

健康检查里重点看两个字段：

- `writable_states.data` 必须是 `ok`（`denied` = 宿主目录属主不对，`missing` = 没挂上）
- `gpg_ledger.never_invoked` 应为空；如果恢复后出现条目，说明账本比清单旧，
  跑一次 `--verify-only` 补上即可

## 与升级的关系

升级镜像**不需要**先恢复备份 —— 数据卷是绑定挂载，重建容器不影响 `./data`。
但两种情况下建议先备份：① 跨大版本升级（v1.4 → v1.5 这种带迁移的）；
② 要改 `ISO_HUB_SECRET_KEY_FILE`、`ISO_HUB_STORAGE_MODE` 这类会影响数据解释方式的配置。
